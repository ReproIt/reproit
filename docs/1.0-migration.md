# Migrating to Repro It 1.0

Repro It 1.0 makes the reproduction contract explicit while preserving readable
1.x inputs. The migration does not require deleting saved repros or rebuilding
production evidence by hand.

## Configuration

Existing `reproit.yaml` files without `schemaVersion` are read as version 1.
New and regenerated files include:

```yaml
schemaVersion: 1
```

A reader rejects a future schema version with a migration repair instead of
guessing at its meaning. Keep authored journeys and saved repros under version
control, then run `reproit doctor` and `reproit check` after an upgrade.

## Production evidence

Repro It no longer exposes Sentry, Datadog, or OpenTelemetry as dedicated
integration contracts. Imported diagnostics may provide context and source
locations, but they are not replay authority. A reproducible occurrence needs
the bounded exchanges and environment evidence captured by the Repro It SDK.
Legacy provider source strings remain readable and normalize to the neutral
`imported-diagnostic` source when rewritten.

This separation keeps a production provider replaceable. It also prevents a
stack trace, event envelope, or monitoring tag from being mistaken for enough
evidence to execute a customer application.

## Occurrences and timestamps

New occurrences use a full, domain-separated content identity. Existing short
legacy identities remain readable, but newly written evidence uses the stronger
form. Callers must treat occurrence identifiers as opaque strings.

New timestamps are canonical RFC 3339 values. Legacy Unix-millisecond strings
remain readable at the version 1 boundary. Invalid or ambiguous timestamps are
rejected instead of silently normalized.

Environment dimensions are bounded, validated, and attached to each
occurrence. One clean replay proves only that occurrence in the environments
covered by its evidence. It does not prove a fix for every device or platform.

## Protocol and release versions

`reproit-protocol` is independently versioned. Its package version and
`contract.json` ledger define the wire versions it reads and writes. CLI and
Cloud versions may move independently only when both satisfy that ledger.

The CLI, Cloud, site, and lab are separate release units. Cloud pins an exact
CLI commit for contract synchronization. Update that pin only after the CLI
changes exist in an immutable commit and the copy check passes.

Source builds use the current stable Rust channel. Container gates use the
official moving distro tags, including `rust:bookworm` and `rust:trixie`, so a
stale compiler pin cannot silently become the supported toolchain.

## Platform support

The generated compatibility ledger is authoritative. The 1.0 support claim
covers every declared atomic target. The generated status records each
target's retained evidence and names any absent evidence as a gap.

Run the native gate for every target used by the application. Evidence must
name the actual operating system, architecture, runtime, reset, and cleanup.
Cross-compilation or an ARM64 emulator cannot stand in for x86_64 native
evidence.

## Compatibility promise

Within 1.x, Repro It preserves documented command behavior, exit meanings, and
machine-readable field meanings. It also preserves configuration schema
version 1, saved repro formats, wire versions, stable identities, and error
distinctions. A breaking meaning change requires a new format or a future major
version. Repro It must dispatch the new format explicitly and provide a
migration path.

Replaceable internals include runners, search strategies, storage engines,
presentation, and CI providers. Those mechanisms may evolve without changing
the initial promises in [the 1.0 contract](decisions/1.0-contract.md).
